# KeyClaim 技术架构

## 为什么必须双端运行

MX Keys 离开某台电脑后，那台电脑的接收器无法再直接控制它。KeyClaim 因此由两台电脑上的本地服务协作：

1. 当前正在被使用的电脑检测本地鼠标或触控板位移。
2. 它通过局域网发送带 HMAC-SHA256 签名的 `Claim` 请求。
3. 当前持有键盘的电脑确认请求方在线、就绪且通道匹配。
4. 持有方通过 Logitech HID++ `0x1814 ChangeHost` 把 MX Keys 切到目标通道。macOS 使用原生 IOKit 回调，Windows 使用 HIDAPI。

局域网通信保留逐网卡签名 UDP 心跳，另有一条持久 TCP 通道作为可靠主链路。对端离线时，Windows 只在真实局域网接口的当前 `/24` 主动发起 TCP 连接，跳过 VMware、WSL、Hyper-V、VPN 等虚拟接口和公网地址。Mac 接受连接后，心跳、召回请求和切换结果都通过同一条已建立连接双向传输，因此不依赖 Windows 接收广播响应或新增入站规则。UDP 仍用于兼容和快速发现；同一召回请求即使从多个通道到达，也会按 nonce 去重，只执行一次 HID++ 切换。

## 关键保护

- 不因系统单纯唤醒而召回，只由实际指针活动触发。
- macOS 在访问接收器前先只读检查“输入监控”授权；未授权时标记服务未就绪，不循环触发系统权限提示。
- 另一台电脑超过 4 秒没有心跳即视为离线，不执行切换。
- 网络消息超过 5 秒即作废，且必须通过配对码签名校验。
- 不设置 2 秒锁定；仅使用默认 60ms 输入防抖和状态幂等。
- 手动 Easy-Switch 按键始终保留为硬件兜底。

## 后台运行

- 用户关闭主窗口时只隐藏窗口，局域网心跳、输入监听和键盘归属服务继续运行。
- 单击菜单栏图标可重新打开窗口，菜单中的“退出 KeyClaim”才会真正结束进程。
- “开机自动运行”在 macOS 使用真实 App 登录项，避免把后台进程显示成无图标的 Unix 可执行文件；由登录项启动时默认不显示主窗口。

## 当前边界

macOS 与 Windows 的第一版输入监听基于全局光标位移，因此触控板可正常触发；远程控制/模拟输入过滤仍是实验性能力。macOS 使用无需辅助功能授权的 AppKit `NSEvent.mouseLocation` 轮询，Windows 使用系统指针查询。后续若需要严格过滤模拟输入，再在 macOS 使用 CGEventTap 的事件来源字段、在 Windows 使用低级鼠标钩子的 injected 标志。

macOS 上当前优先选择 `0xC52B` Unifying 接收器；非 Unifying 设备会再通过 `0x0005` 设备类型能力确认键盘。这样不会误把本机的 Bolt 鼠标当成 MX Keys。
