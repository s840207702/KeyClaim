# KeyClaim 技术架构

## 为什么必须双端运行

MX Keys 离开某台电脑后，那台电脑的接收器无法再直接控制它。KeyClaim 因此由两台电脑上的本地服务协作：

1. 当前正在被使用的电脑从系统原生输入事件流检测本地鼠标或触控板位移。
2. 它通过局域网发送带 HMAC-SHA256 签名的 `Claim` 请求。
3. 当前持有键盘的电脑确认请求方在线、就绪且通道匹配。
4. 持有方通过 Logitech HID++ `0x1814 ChangeHost` 把 MX Keys 切到目标通道。
5. 目标方通过本机接收器探测到 MX Keys 上线后发送最终确认；在此之前只显示“指令已送达”。

持久 TCP 是可靠主链路。对端离线时，Windows 只在真实局域网接口的当前 `/24` 主动发起连接，跳过 VMware、WSL、Hyper-V、VPN 等虚拟接口和公网地址。Mac 接受连接后，心跳、召回请求和切换结果都通过同一条连接双向传输，发送不依赖 UDP 端口是否成功绑定。UDP 只保留低成本广播兼容，不再执行会阻塞事件循环的逐地址网段扫描；同一召回请求即使从多个通道到达，也会按 nonce 去重，只执行一次 HID++ 切换。应用层使用单实例保护，避免后台旧进程与新版本拆分占用 UDP/TCP 端口。

## 关键保护

- 不因系统单纯唤醒而召回，只由实际指针活动触发。
- macOS 在访问接收器前先只读检查“输入监控”授权；未授权时标记服务未就绪，不循环触发系统权限提示。
- 另一台电脑超过 4 秒没有心跳即视为离线，不执行切换。
- 网络消息超过 5 秒即作废，且必须通过配对码签名校验。
- 不设置 2 秒锁定；90ms 内累计低速位移，并使用默认 60ms 输入防抖。
- `ChangeHost` 按 fire-and-forget 发送，因为设备成功切换时会先断开而无法回复。
- 召回请求使用固定 nonce 短时重发，目标端上线才完成状态迁移。
- 手动 Easy-Switch 按键始终保留为硬件兜底。

## 后台运行

- 用户关闭主窗口时只隐藏窗口，局域网心跳、输入监听和键盘归属服务继续运行。
- 单击菜单栏图标可重新打开窗口，菜单中的“退出 KeyClaim”才会真正结束进程。
- “开机自动运行”在 macOS 使用真实 App 登录项，避免把后台进程显示成无图标的 Unix 可执行文件；由登录项启动时默认不显示主窗口。

## 原生输入边界

macOS 使用位于 HID 事件入口的只读 `CGEventTap`，监听鼠标移动、拖动和滚动；触控板产生的指针事件使用同一通路。带有进程来源的合成事件会被过滤。Windows 使用后台 message-only window 注册 Raw Input mouse usage，只处理系统交付的真实鼠标 HID 数据，不依赖全局光标坐标，也不会把程序移动指针误认为用户意图。

原生层只上报位移和“是否合成”，Rust 仍然是输入意图、通道状态和召回协议的唯一数据源，避免把业务状态复制到 AppKit/Win32 桥接层。监听线程退出后会标记未就绪并自动重试。

## 休眠边界

纯软件无法命令一把当前连接在已深度休眠电脑上的键盘离开，因为只有当前持有方能发送 `ChangeHost`。KeyClaim 会短时重试并明确显示“持有方可能休眠”，不会伪造成功；两台电脑处于唤醒或可处理后台任务状态时，双本地鼠标召回链路完整工作。

macOS 上当前优先选择 `0xC52B` Unifying 接收器；非 Unifying 设备会再通过 `0x0005` 设备类型能力确认键盘。这样不会误把本机的 Bolt 鼠标当成 MX Keys。
